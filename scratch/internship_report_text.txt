ABSTRACT
Green-Scheduler is a carbon-aware job scheduling pipeline designed to transform GreenOps principles into an automated infrastructure policy. The project implements a Gatekeeper Pattern that evaluates whether a flexible workload should execute immediately or be delayed until the electricity grid becomes cleaner. This practice, known as temporal shifting, is intended to reduce the carbon footprint of compute-intensive workloads such as machine learning training, batch processing, and CI/CD tasks.
The system is built using a React-based dashboard for workload submission and monitoring, a FastAPI backend for orchestration, SQLite for persistence, and the ElectricityMaps API for real-time carbon-intensity information. A policy-driven decision engine compares current grid carbon intensity against configurable sustainability thresholds defined for low-, medium-, and high-priority jobs. If the grid is sufficiently clean, the workload is executed; otherwise, it is delayed until sustainability conditions are satisfied. In addition to carbon reduction, the project demonstrates alignment with FinOps goals because low-carbon time windows may also correlate with lower spot-instance pricing and better resource efficiency. The system concludes by generating a PDF sustainability certificate containing execution details, grid parameters, and audit evidence. This report presents the design, implementation, workflow, and expected impact of the Green-Scheduler system.
Keywords: GreenOps, FinOps, Carbon-Aware Scheduling, Temporal Shifting, FastAPI, React, Sustainability, CI/CD.

Introduction
Green-Scheduler is a carbon-aware scheduling system designed to operationalize sustainability in software infrastructure. The project focuses on flexible compute workloads such as machine learning jobs, batch processing, and CI/CD tasks, and determines whether they should execute immediately or wait until the power grid has lower carbon intensity.
The central goal of the system is to convert GreenOps from a conceptual recommendation into an automated policy mechanism. Instead of asking users or administrators to manually choose a greener execution time, the platform makes this decision using live carbon-intensity data and a configurable rule engine.
This approach is important because digital workloads increasingly contribute to indirect carbon emissions through electricity usage. By introducing carbon awareness into job scheduling, the project demonstrates how environmental responsibility can be integrated into software architecture and platform operations.
1.1 Project title, scope, and definition
The project title is Green-Scheduler: Carbon-Aware Job Scheduling Pipeline. The scope of the project includes design and implementation of a full-stack platform that accepts Python-based workloads, classifies their execution priority, checks live grid carbon intensity, applies sustainability rules, and either executes or delays the job based on policy.
The system also includes logging, auditability, and automatic generation of a sustainability certificate after execution. The project is limited to flexible workloads and does not attempt to schedule hard real-time or mission-critical tasks that must run immediately.
1.2 Problem statement
Many computing workloads are executed immediately without considering whether the electricity grid is currently being powered by cleaner or dirtier energy sources. This leads to avoidable carbon emissions, especially for workloads that could be delayed with little or no operational impact.
The problem addressed by this project is the lack of an automated mechanism that incorporates environmental conditions into infrastructure-level execution decisions. Green-Scheduler addresses this by introducing carbon-aware gating before job execution.
1.3 Objectives
The major objectives of the project are listed below:
To build a system that accepts and manages flexible compute workloads.
To classify workloads according to execution priority.
To fetch real-time carbon-intensity information from an external API.
To enforce sustainability policies through an automated decision engine.

Motivation
Modern organizations optimize infrastructure primarily for performance, availability, and cost, but environmental impact is now becoming equally significant. A large number of workloads do not require immediate execution and can therefore be shifted in time without affecting critical business functions.
This project is motivated by the idea that flexible compute jobs can be scheduled during lower-carbon electricity windows. Such temporal shifting allows organizations to reduce emissions without changing application logic or relocating infrastructure.
An additional motivation is the economic benefit of better workload timing. Since low-carbon periods may also align with favorable resource pricing or better compute availability, the project creates a bridge between sustainability goals and FinOps optimization.
Literature Review
Green-Scheduler is based on the concept that software systems can reduce environmental impact by making runtime decisions according to grid conditions. This work is closely related to emerging themes in sustainable computing, cloud optimization, ML-Ops, and carbon-aware infrastructure.
The project implements the Gatekeeper Pattern, where each workload must pass through a decision checkpoint before execution. In this model, the scheduler acts as a policy-enforcement layer rather than a passive monitoring tool.
Temporal shifting is the primary conceptual foundation of the system. Instead of moving workloads geographically, the project shifts them in time so that energy-intensive processing can occur during cleaner electricity windows.
Carbon-aware computing has emerged as an important research direction because conventional workload scheduling often optimizes only for performance, latency, or cost, while ignoring the carbon intensity of electricity at the time of execution. Recent research on carbon-aware scheduling shows that greenhouse-gas reductions can be achieved by making scheduling decisions based on time-varying grid emissions, and some studies report reductions of up to 47.6% with only limited impact on makespan. This line of work is especially relevant to flexible workloads, where execution can be delayed without violating strict business constraints.
A central concept in this field is temporal shifting, which means moving workloads from one time window to another so that they run when the electricity supply is cleaner. Instead of relocating workloads geographically, temporal shifting uses the variation in renewable-energy availability and carbon intensity throughout the day to reduce emissions. This approach is practical because many tasks in cloud and platform environments, such as batch jobs, analytics pipelines, model training, and CI/CD jobs, are delay-tolerant and therefore suitable for environmentally informed scheduling.
GreenOps has developed as an operational discipline that formalizes this sustainability perspective in cloud infrastructure. Forrester defines GreenOps as the practice of minimizing a cloud environment’s carbon footprint through efficient use of cloud resources, while also recognizing that emissions depend on broader factors such as electricity source, data movement, infrastructure footprint, and cooling efficiency. This is important because cloud sustainability is not achieved only through efficient servers; it also depends on how and when workloads are run, what regions are used, and how much waste exists in the overall system.
The relationship between GreenOps and FinOps is particularly important in the literature because both disciplines aim to improve resource efficiency. Forrester notes that the same activities used in FinOps, such as right-sizing, deleting idle resources, and scheduling compute off-time, can also reduce carbon emissions, and describes cost as a close proxy for sustainability in many operational contexts. Similarly, research on FinOps for sustainable cloud engineering argues that cloud monitoring, cost allocation, budgeting, and forecasting can be integrated into a unified optimization strategy that improves both economic and operational efficiency. This overlap supports the idea that carbon-aware scheduling is not only an environmental initiative but also a cost-management opportunity.
Another recurring theme in the literature is the need for real-time or near-real-time carbon signals. Carbon-aware scheduling depends on visibility into grid intensity, which can change significantly based on renewable generation mix, demand, and regional power characteristics. This has led to increased interest in platforms and APIs that expose carbon-intensity metrics to infrastructure systems so that scheduling decisions can be made automatically rather than manually. In practical terms, this means that a scheduler can use live environmental data the same way traditional systems use CPU, memory, or queue length metrics.
Research also shows that carbon-aware scheduling is not limited to centralized cloud data centers. Work on edge-fog and distributed systems proposes carbon-aware task allocation algorithms that adjust execution based on renewable availability and real-time carbon intensity while maintaining acceptable task completion times. These studies are significant because they demonstrate that sustainability-aware scheduling can be generalized across different computing environments, from cloud orchestration to IoT-driven edge infrastructures. Although Green-Scheduler is focused on a software-platform use case, the same conceptual model applies across these broader distributed systems.
In workflow systems, scheduling complexity increases because tasks may have dependencies, precedence constraints, or fixed resource mappings. Recent work on carbon-aware workflow scheduling highlights that emission reduction is more effective when schedulers account not only for carbon intensity over time but also for workflow structure and execution dependencies. This finding is relevant because it suggests that future versions of systems like Green-Scheduler could move beyond single-job approval and support multi-stage workflows with dependency-aware optimization.
The literature also emphasizes that carbon optimization should not be treated as an isolated metric. Sustainable scheduling introduces trade-offs among emissions, execution time, reliability, cost, and service guarantees. In many real-world settings, not every task can be delayed, so researchers often propose priority-sensitive or policy-based systems that distinguish urgent workloads from flexible ones. This directly supports the design of Green-Scheduler, where job priority influences the maximum acceptable carbon threshold and therefore determines whether a task is delayed or executed immediately.
A further contribution of recent GreenOps discourse is its emphasis on observability and accountability. Sustainability claims are increasingly expected to be backed by measurable evidence, especially under emerging regulatory pressure and ESG-related reporting requirements. Forrester notes that regulatory and stakeholder expectations are pushing organizations to monitor emissions more closely and to use tools that make carbon impact visible at the infrastructure level. This supports the inclusion of audit logs, grid parameters, and report-generation features in systems like Green-Scheduler, where the sustainability certificate acts as an evidence artifact rather than a purely decorative output.
From an implementation perspective, much of the literature points toward automation as the missing link between sustainability theory and actual infrastructure behavior. Many organizations understand the value of reducing carbon impact, but without policy engines, monitoring integrations, and scheduler-level controls, sustainability remains advisory rather than enforceable. Green-Scheduler addresses precisely this gap by embedding environmental checks into the job-execution path, turning sustainability into an operational decision rather than a post-hoc analysis.
Overall, the literature supports the core premise of Green-Scheduler: delay-tolerant workloads can be scheduled more intelligently by combining live carbon-intensity information, workload classification, and policy-based execution controls. Research on carbon-aware scheduling demonstrates meaningful emission reductions, GreenOps explains the operational framework for sustainable cloud behavior, and FinOps literature shows that efficiency-driven controls can simultaneously support economic and environmental outcomes. Together, these strands establish a strong academic foundation for a carbon-aware job scheduling pipeline that is both technically feasible and practically relevant.

6.1 Workload submission
A user submits Python code through the React-based dashboard. The request is transmitted to the FastAPI backend and stored for further evaluation.
6.2 Job classification
The backend scans the submitted code to infer priority. If the code contains libraries such as fastapi or flask, the job is treated as high priority. If it contains pandas, numpy, or tensorflow, it is treated as medium priority. Otherwise, it defaults to low priority.
6.3 The green check
The system fetches current carbon intensity from the ElectricityMaps API for the configured region. This value acts as the environmental input to the scheduling decision.
6.4 Decision engine
The intensity value is compared against the thresholds defined in sustainability_policy.yaml. If the current grid condition is cleaner than the threshold permitted for the job’s priority, execution is approved. Otherwise, the workload is delayed.
6.5 Execution and audit
Approved workloads are run using Python’s subprocess mechanism. Execution logs, duration, and job status are stored, and a PDF sustainability certificate is generated at the end.

8.2 Level 1 : System Overview
The Level 1 DFD expands the single process shown in Level 0 into the major internal processes of the Green-Scheduler application. It provides a system-wide view of how a workload flows through submission, evaluation, execution, and reporting stages.
The process begins with 1.0 Manage Job Submissions, where the Developer or User submits the job details and applicable policy. The next major process is 2.0 Evaluate Carbon Intensity, which retrieves pending jobs and their thresholds from the database and sends an API request to the external carbon service. If the carbon intensity is within the acceptable threshold, the process triggers 3.0 Execute Workload, which dispatches the workload to the execution cluster. The execution cluster processes the job and sends back completion information and energy metrics. These outputs are then forwarded to 4.0 Generate Audit Report, which prepares the final sustainability report in PDF format. 8.2 Level 2 : Deep Dive into Process 2.0
The Level 2 DFD provides a more detailed decomposition of Process 2.0: Evaluate Carbon Intensity, which is the most critical decision-making component in the Green-Scheduler system. This level demonstrates the internal micro-steps involved in determining whether a workload should be executed immediately or deferred until cleaner grid conditions are available.
The process starts with 2.1 Retrieve Pending Jobs, where the system reads pending job details from the job database. Along with these jobs, the system also considers the corresponding thresholds, limits, and target execution regions associated with each workload. The next step is 2.2 Fetch Region Carbon Data, in which the system sends an API request to the external carbon service and retrieves real-time carbon intensity values in grams of carbon dioxide equivalent per kilowatt-hour (gCO2eq/kWh).
After fetching the current grid data, the system performs 2.3 Evaluate Policy vs. Intensity. In this step, the live carbon intensity is compared with the threshold defined for the job’s assigned priority level. The evaluation result is then categorized as either pass or fail depending on whether the measured carbon intensity satisfies the sustainability policy.
Finally, the system enters 2.4 Update Schedule State, where the scheduling decision is applied. If the evaluation result indicates that the grid conditions are clean enough, the system generates an execution trigger and forwards the workload to 3.0 Execute Workload. If the result indicates that the carbon intensity is too high, the job status is updated to delayed in the job database, and the workload remains pending until the next evaluation cycle.

14.1  Scenario A: Execution During High Carbon Intensity (Low Priority)
To validate the scheduler’s ability to defer non-critical workloads under unfavorable environmental conditions, a background data-cleanup script was submitted to the system as a Low Priority job. According to the configured sustainability policy, low-priority workloads are permitted to execute only when the grid carbon intensity is at or below 50 gCO2eq/kWh. During this test, the external carbon-intensity service returned a real-time grid value of 721 gCO2eq/kWh, which was significantly higher than the allowable threshold.
Once the job was submitted, the Green-Scheduler pipeline classified the workload, retrieved the applicable policy threshold, and initiated the carbon-check process through the external API. The decision engine then compared the reported intensity against the threshold defined for low-priority jobs and correctly determined that the workload should not be executed at that time. As a result, the system updated the job state in the database to Delayed and withheld dispatch to the execution environment, thereby preventing unnecessary workload execution during a carbon-intensive period.
This scenario confirms that the proposed system can successfully implement temporal shifting for non-urgent workloads. By deferring execution until cleaner grid conditions are available, the scheduler demonstrates its ability to translate sustainability policy into an enforceable runtime decision rather than leaving it as a manual recommendation. The result also highlights the practical value of the gatekeeper model, in which environmental conditions directly influence infrastructure behavior before resource consumption occurs
14.2 Scenario B: Execution During Acceptable Grid Conditions (High Priority
To verify the successful execution path of the scheduling pipeline, a critical machine-learning training workload was submitted as a High Priority job. In the current sustainability policy, high-priority workloads are allowed to execute at a more relaxed threshold of 250 gCO2eq/kWh, reflecting their greater operational importance. Under this scenario, the grid carbon intensity was within the acceptable limit, which allowed the system to approve execution.
The workflow began with job submission through the interface, followed by workload classification and policy mapping. The backend then invoked the carbon-intensity check and compared the returned value with the threshold for high-priority tasks. Since the environmental condition satisfied the configured policy, the decision engine generated an execution trigger and dispatched the workload to the execution component. The system then completed the workload in 0.08 seconds, captured execution logs, and automatically generated the PDF Sustainability Audit Certificate as proof of compliant execution and audit completion.
This scenario demonstrates that the Green-Scheduler does not merely delay workloads, but also supports smooth and timely execution when sustainability conditions are met. The result verifies the full positive workflow of the system, including policy evaluation, dispatch, execution, logging, and certificate generation. It also shows that carbon-aware scheduling can be integrated into practical software pipelines without interfering with the successful completion of important workloads.
14.3 Workflow Explanation Across Scenarios
The two scenarios collectively explain the functional behavior of the Green-Scheduler pipeline under different environmental conditions. In both cases, the workflow begins with job submission and static analysis of the code to infer the workload’s priority level. Once the priority is determined, the system reads the corresponding policy threshold from the sustainability configuration and sends a request to the ElectricityMaps service for current regional carbon-intensity data.
After receiving the real-time carbon data, the decision engine compares the measured intensity with the allowable threshold for the submitted workload category. If the value exceeds the threshold, the system records the job as delayed and retains it in the scheduling pipeline for future reevaluation. If the value is within the acceptable limit, the workload is approved, dispatched to the execution environment, and monitored until completion. Once execution ends, the audit module records execution logs, captures environmental context, and generates the sustainability certificate.
This workflow demonstrates that the system is capable of handling both deferred and approved execution paths using the same policy-driven architecture. As a result, Green-Scheduler supports consistent, traceable, and auditable carbon-aware operations across different workload categories and varying grid conditions.
14.4 Performance and Latency
The implementation of the carbon-aware decision engine introduced only minimal additional overhead into the normal job-submission pipeline. Because the main added step is an API-based carbon-intensity lookup followed by a threshold comparison, the architecture remains lightweight and suitable for practical deployment. Electricity Maps describes its platform as a real-time electricity grid API intended for dynamic applications such as monitoring, load shifting, and flexibility-aware decision systems, which supports the use of such integrations in operational scheduling workflows.
In the current project implementation, API response times were observed to remain within an acceptable range, and the additional latency introduced by the carbon-check stage was small compared to the overall workload lifecycle. The system therefore demonstrates that carbon-aware routing can be incorporated into a FastAPI-based orchestration pipeline without creating a significant performance bottleneck, particularly for delay-tolerant jobs such as batch processing, analytics, and model training.
From a system-design perspective, this is an important outcome because one of the common concerns in sustainable scheduling is whether environmental intelligence will slow down job processing. The observed behavior indicates that the added sustainability logic remains operationally feasible, especially when paired with asynchronous API handling and lightweight backend orchestration. Hence, the project confirms that carbon-aware decision making can be introduced into modern software systems with limited impact on responsiveness while still delivering measurable sustainability benefits.

Conclusion
Green-Scheduler demonstrates how GreenOps principles can be translated into a practical and automatable software system. By combining real-time carbon-intensity checks, configurable policy rules, workload prioritization, and PDF-based audit reporting, the project creates a meaningful approach to sustainable job orchestration.
The project is academically relevant because it connects software architecture, cloud engineering, environmental sustainability, and cost optimization into a single implementation. It is also industrially relevant because it shows that organizations can pursue carbon-aware operations without significantly disrupting existing workload patterns.
Overall, the project provides a strong foundation for future work in sustainable computing and carbon-aware infrastructure engineering.
